# 对题目的补充思考

以下是实现过程中形成的 11 点判断。它们不是功能清单，而是对“为什么这样做”和“哪里仍不应自动化”的取舍说明。

## 1. 记账主体是所有 AR/AP 结论的隐含前提

题目要求“结合签发方、接收方、当前记账主体和收费方向”判断 AR/AP，但题目没有给出记账主体。这意味着：

- AR/AP 不是文档的固有属性，而是“谁在记账”的函数；
- 同一张 Debit Note，对签发方是 AR，对接收方是 AP；
- 如果主体同时出现在签发方和接收方，或者两边都不出现，正确做法不是猜，而是 `PENDING_REVIEW`。

因此本项目把主体放进配置，并支持 `--entity` / `--entity-alias` 覆盖；输出 `financial_attributes.accounting_entity` 明确记录本次使用的视角。生产接入时，主体应来自登录用户或公司实体主数据，而不是从单据文本推断。

## 2. 非账单文档不应被“静默丢弃”

题目要求识别 Debit Note、Credit Note、Invoice 等，但真实业务里，费用经常先出现在 PRE-ALERT、到港通知或邮件正文中。如果系统只处理“账单”，就会漏掉最早的入账信号。

取舍是：非账单文档中的有效费用仍然生成记录，默认按配置 `CREATE`，但在 `audit_trail.document_kind` 中保留来源类型，并在原因中说明“AR/AP 待人工确认”。这样既保留召回，又让下游知道这不是正式账单。若财务政策不允许，配置可改为 `PENDING_REVIEW`。

## 3. OCR 是召回工具，不是事实来源

OCR 对扫描件是必需的，但 OCR 结果本身可能错：`0/O`、`1/I`、小数点丢失、表头串行。直接把 OCR 金额入账，是这类系统最危险的设计。

本项目的处理是：

- 同时保留 PDF 原生文本与 OCR 结果；
- 原生文本有费用行时优先采用原生；
- 原生与 OCR 数量或合计不一致时，写入 note 并保留 OCR 供审计；
- OCR 金额修正在证据中记录 `OCR 金额修正: 1O.50 -> 10.50`；
- OCR 修正会触发校验告警，而不是静默修正；
- 无法验证的 OCR 结果走 `PENDING_REVIEW`。

## 4. 更新的本质是“增量补丁”，不是“整单覆盖”

题目要求“只修改输入材料明确要求变更的字段，其他字段继承原账单”。这听起来简单，但实现上有两个陷阱：

1. 不能用候选值整体覆盖已有值；候选值缺失不代表要清空；
2. 不能因为某个字段“看起来变了”就更新，必须有该字段的证据。

因此 `build_update_patch` 只生成白名单字段，并且金额、币种、付款方式、数量、单价都要求对应 `FieldEvidence`。未出现在补丁中的字段在输出时继承已有账单值，并在 `inherited_fields` 中列出。这样 UPDATE 是幂等、可审计的。

## 5. 重复有两个层面，必须分开处理

- **文件级重复**：同一文件、同一哈希。解析层直接去重，记录 `duplicate_of`，不产生第二条业务记录。
- **业务级重复**：不同文件描述同一笔费用。系统用“单据号/提单号/订舱号/交易双方+日期+费用名+金额+币种”生成 CREATE key；同批次内重复时保留证据最强的一条，其余转 `PENDING_REVIEW`。

如果只做文件级去重，同一封邮件转发的 PDF 和图片会重复建账；如果只做业务级去重，又会把同一文件内的两条合法相同费用误杀。两层分开，才能兼顾。

## 6. 匹配歧义是正常状态，不是异常

运费、附加费在不同账单中可能同名同币种。只按“单据号 + 费用名”匹配，遇到两行同名费用时无法判断该更新哪一行。

本项目的匹配规则是有序的，并且允许候选集：

1. 单据编号 + 费用名称；
2. 提单号 + 费用名称 + 币种；
3. 订舱号 + 费用名称 + 币种；
4. 箱号 + 交易双方 + 日期 + 金额。

候选多于一条时，用金额/单价/数量/付款方式做消歧；仍然无法唯一确定时输出 `PENDING_REVIEW`，而不是取第一条。这个设计把“不确定”显式化，避免静默错改。

单据编号匹配也不是无条件信任。单号可能被复用，OCR 也可能把相邻字符并入箱号或发票号。因此参考匹配成功后仍复核主/分提单号、箱号与单据日期；任一冲突都转人工。箱号本身先通过 ISO 6346 校验位过滤，避免把发票号当作箱号参与匹配。

## 7. LLM 只应做“受限补充”，不能做最终裁判

LangChain/LLM 的价值在于理解非结构化表达（多语言、非标准措辞、版式变化），但它不适合决定金额和 AR/AP。项目的约束是：

- 规则先抽取，LLM 只补缺失字段；
- LLM 返回的每个字段必须能在原文或 OCR 文本中找到证据，否则拒绝；
- LLM 不允许放宽校验规则；
- LLM 失败、超时或无密钥时，系统回退到规则结果，不阻塞整批；
- 提示词版本和模型信息写入审计。

这不是“不信任 LLM”，而是把 LLM 的输出放进可验证的边界内。

## 8. 幂等与批次重放应成为一等需求

财务批处理经常需要重跑：网络失败、上游补发、人工修正。如果系统每次重跑都 CREATE，就会制造重复账。

除了业务级重复检测，建议生产版增加：

- 输入批次指纹（文件哈希集合）与输出批次号；
- 下游写入使用 `record_id` 或业务幂等键；
- 重放时先查已有账，再决定 CREATE/UPDATE/NO_CHANGE。

本项目已保留 `run_id`、`record_id`、`source_sha256` 和 manifest，足以作为幂等键的基础。

## 9. 人工审核不是失败，而是产品的一部分

把自动入账率当成唯一目标，会诱导系统在证据不足时“猜一个”。更合理的指标体系是：

- 自动入账的准确率；
- 不安全自动入账率（应为 0）；
- 审核队列的命中率与可解释性；
- 人工处理一条 PENDING 的平均时间。

因此每条 PENDING_REVIEW 都带 `review_reasons`、阻断性校验结果、匹配候选和字段证据。审核人员不需要重新解析文件，只需要做判断。

## 10. 隐私与外部调用需要默认最小化

账单和邮件包含公司名、联系人、邮箱、账号、运价。系统默认：

- 只把 PDF/图片上传给题目指定的 OCR 服务，不上传其他文件；
- 审计文本中的邮箱、账号做脱敏；
- LLM 只接收截断后的必要文本，不接收密钥；
- `template_key.txt` 不进入仓库，示例文件只保留占位符；
- 原始 OCR 响应与缓存可关闭或定期清理。

这些不是“以后再做”的安全项，而是接入真实数据前必须默认开启的边界。

## 11. 币种缺失必须转人工审核，不能猜测

金额和币种是一个整体。缺少币种时，金额本身无法安全入账：无法确定本位币金额，无法进行汇率换算，也无法保证 AR/AP 统计口径正确。

本项目对币种缺失的处理是：

- OCR 或文档解析未提供币种时，`currency` 保持 `null`，不根据发票语言、交易方所在地、其他金额或历史账单自行推断；
- 校验产生阻断性 `MISSING_CURRENCY`，该费用行进入 `PENDING_REVIEW`；
- `financial_attributes.posting_type` 保持 `null`，避免在币种未知时继续推导 AR/AP；
- `review_reasons` 明确列出缺少币种，审核人员只需确认或补充该字段；
- 如果 OCR 服务返回 `currency`、`currencyCode`、`ccy` 或 `cur`，适配层会保留并写入证据；只有确实缺失时才转审核；
- 不使用默认币种兜底，也不从已匹配账单自动继承。匹配到已有账单只能证明业务关联，不能替代源单据的币种证据。若未来业务允许继承，应作为显式策略并记录审计。

图片样例就是该策略的实例：OCR 的费用明细只返回费用名与金额，没有返回图片上清晰可见的 `USD`。系统没有猜测币种，而是将该费用行标记为 `PENDING_REVIEW`。这是有意的保守设计：宁可多一次人工确认，也不产生一条币种错误的财务记录。
